# Research: OAuth-proxied exchange custody for agent trading (vs BYOK)

*2026-07-09. Grounding survey for `docs/cex-oauth-proxy-design.md`. Three axes: production practice, standards, academic literature. Every source verified against its authoritative host per the integrity protocol; confidence noted per source; one fabrication-suspect arXiv item quarantined and excluded.*

## Question

Should agent-initiated CEX trading run through platform-custodied OAuth grants (the user's venue credential never exists client-side) proxied by the MCP server, instead of — or alongside — BYOK (user-held API keys)? What does the field require such a design to satisfy?

## Where the field is

**Production practice.** Every serious "third party accesses your account" system has converged on aggregator custody with opaque client handles: Plaid holds the bank-side credential and hands clients only a revocable, product-scoped `access_token` ([plaid.com/docs/api/items](https://plaid.com/docs/api/items/), HIGH); Coinbase delegates trading via OAuth with 1-hour access tokens and single-use rotating 1.5-year refresh tokens, now enforcing portfolio-scoped grants server-side ([docs.cdp.coinbase.com OAuth overview/quickstart](https://docs.cdp.coinbase.com/coinbase-app/oauth2-integration/overview), HIGH); Kraken Connect adds the distinctive twist we build on — the OAuth token cannot call private endpoints at all; a scoped **ephemeral Fast API key** is minted per use ([docs.kraken.com Kraken Connect](https://docs.kraken.com/api/docs/oauth/kraken-connect/), corroborated line-by-line by our production adapter, HIGH). Order attribution to a partner is universal across crypto venues, in three encodings: dedicated body field (Kraken `broker` — [change log](https://docs.kraken.com/api/docs/change-log/), MEDIUM-HIGH), client-order-id prefix (Binance Link `x-<BROKERID>` — [binance.com FAQ](https://www.binance.com/en/support/faq/how-to-set-up-the-api-link-id-a78a065d0c4846aaa1af474d8e712ab9), MEDIUM-HIGH), HTTP header (Bybit `Referer` — [bybit-exchange.github.io](https://bybit-exchange.github.io/docs/v5/guide), MEDIUM-HIGH), plus OKX `tag` ([okx.com/docs-v5/broker_en](https://www.okx.com/docs-v5/broker_en/), MEDIUM-HIGH). IBKR's introducing-broker model shows the structural (master/sub-account) variant ([interactivebrokers.com Web API](https://www.interactivebrokers.com/campus/ibkr-api-page/web-api-account-management/), HIGH).

**Standards.** The MCP authorization spec (rev 2025-11-25) regulates exactly our topology and *mandates* the custody boundary: an MCP server **MUST NOT pass through** the token it received from the MCP client to upstream APIs; upstream access uses separate credentials; confused-deputy defenses are spelled out ([modelcontextprotocol.io authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), HIGH). RFC 8628 (Device Authorization Grant) is the canonical "start on a constrained client, consent in a browser" pattern with the security considerations our consent handoff must inherit (user-code entropy, remote-phishing §5.4) ([rfc-editor.org/rfc/rfc8628](https://www.rfc-editor.org/rfc/rfc8628), HIGH). RFC 8693 (Token Exchange) supplies delegation-vs-impersonation semantics and the `act`/`may_act` audit vocabulary for the MCP-server→platform acting-user hop ([rfc-editor.org/rfc/rfc8693](https://www.rfc-editor.org/rfc/rfc8693), HIGH); Microsoft's OBO flow is its production embodiment, with the delegated-scopes-only and never-relay-downstream-tokens lessons ([learn.microsoft.com OBO](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow), HIGH). RFC 9700 (OAuth Security BCP) + RFC 7636 (PKCE) define the code-flow hygiene floor ([rfc9700](https://www.rfc-editor.org/rfc/rfc9700), [rfc7636](https://www.rfc-editor.org/rfc/rfc7636), HIGH); FAPI 2.0 is the financial-grade benchmark to meet on surfaces we control and gap-table against on the venue leg ([openid.net FAPI 2.0](https://openid.net/specs/fapi-security-profile-2_0-final.html), HIGH).

**Academic.** Fett/Küsters/Schmitz's formal OAuth analysis (ACM CCS 2016, [dblp](https://dblp.org/rec/conf/ccs/FettKS16.html), HIGH) and the FAPI formal analysis (IEEE S&P 2019, [dblp](https://dblp.org/db/conf/sp/sp2019.html), HIGH) give the attack classes (mix-up, state/CSRF, code injection, 307 leakage) our flow must close; Sun/Beznosov (CCS 2012, [dblp](https://dblp.org/rec/conf/ccs/SunB12.html), HIGH) is the empirical argument for **one audited OAuth implementation** over every client rolling its own — the core anti-BYOK datum. Macaroons (NDSS 2014, [ndss-symposium.org](https://www.ndss-symposium.org/ndss2014/ndss-2014-programme/macaroons-cookies-contextual-caveats-decentralized-authorization-cloud/), HIGH) formalize attenuation-only delegation — the theory behind our per-call minted keys (each key ⊆ grant, caveated by permission set and lifetime). South et al., "AI Agents Need Authenticated Delegation" (ICML 2025 oral, [icml.cc](https://icml.cc/virtual/2025/oral/40173), HIGH) prescribes extending OAuth with auditable, scoped human→agent delegation chains — our architecture is that prescription instantiated for exchange custody. *Honesty note: beyond the ICML paper, LLM-agent authorization work is preprint/IETF-draft grade; we cite only what verified. Quarantined as likely fabricated: "AIP: Agent Identity Protocol" (arXiv 2603.24775 — implausible ID, no dblp/proceedings corroboration).*

## Minimum principles the design must satisfy

1. **Hard custody boundary, spec-mandated**: venue tokens never leave the platform; the agent's credential never reaches the venue (MCP spec MUST NOT + Microsoft OBO warning).
2. **Audience binding on every credential** (MCP spec / RFC 8707 / RFC 9700).
3. **Delegation, not impersonation** — every action carries (subject = user, actor = agent/key/service), RFC 8693 `act`-shaped audit chain; supported by ICML 2025.
4. **Code-flow hygiene** per RFC 9700/7636: PKCE S256 even as a confidential client, exact redirect-URI match, single-use `state` cryptographically bound to the initiating session, no tokens in URLs.
5. **Consent handoff inherits RFC 8628 §5**: the consent page states which agent/session initiated; artifacts single-use, short-expiry, rate-limited.
6. **Consent is complete and upfront** (Microsoft OBO combined-consent lesson): the one browser consent must enumerate downstream powers; withdrawals structurally impossible (never request `funds-withdraw`-class scopes for trading).
7. **Attenuation-only per-call credentials** (Macaroons): minted key ⊆ grant, split read-path vs trade-path permission sets, TTL-bounded, deleted after use, crash-orphan self-heal documented.
8. **Refresh-token rotation designed in** (Coinbase single-use rotation is the norm; FAPI 2.0 notes rotation fragility — pick deliberately and record why).
9. **Revocation severs the chain immediately** at both ends (Plaid `/item/access_token/invalidate` precedent); consent-expiry errors surface to the agent as actionable re-consent signals, not opaque 500s.
10. **Documented deviations**: API-key (not OAuth 2.1) on the agent↔MCP hop; RFC 8628 as pattern not wire protocol; RFC 8693 as internal model not public STS; FAPI gaps on the venue leg are venue-capability constraints compensated by custody.

## Adopt / defer

**Adopt now:** Plaid-style custody posture; Kraken ephemeral key mint with per-path permission split (already shipped, live-verified 2026-07-09); dedicated-field broker attribution on every order incl. validate-only (already shipped on three surfaces); MCP token-passthrough prohibition as the proxy contract; RFC 8693 delegation semantics for the acting-user hop; RFC 9700 checklist on the connect flow; single audited OAuth implementation (platform) — no client-side OAuth ever.

**Defer (tracked in the epic):** OAuth 2.1 on the agent↔MCP hop (API key now; spec-aligned for STDIO, documented deviation for HTTP); sender-constrained (DPoP/mTLS) tokens toward venues (venue-capability-bound); FAPI 2.0 full conformance table; distributed per-user mint lock (needed before horizontal scale); completion-by-state consent page (v1 reuses the signed-in platform callback); Coinbase as second OAuth venue.

**Avoid:** client-order-id-prefix attribution (burns idempotency space — Binance's design, not ours); BYOK as the *primary* path (long-lived unattenuable bearer keys, per-user DIY OAuth — CCS 2012's exact failure mode); treating the venue OAuth token as a trading credential (Kraken rejects Bearer on `/0/private`); assuming non-expiring consent (PSD2 90-day windows exist).

## The delta (contribution statement)

No surveyed system composes all four properties we combine: **(a)** platform-custodied venue OAuth grants (Plaid has this, for banking data, not trading); **(b)** per-call, least-privilege, *path-split* ephemeral venue keys — read paths structurally cannot trade (Kraken enables the mint; no surveyed integrator splits permission sets per call path); **(c)** venue-native broker attribution injected server-side on every order including validate-only, so revenue attribution is tamper-proof and not caller-controlled; **(d)** an MCP resource-server front conforming to the 2025-11-25 authorization spec's token-passthrough prohibition, so agents act for users with zero venue-credential exposure and an RFC 8693-shaped delegation audit chain. BYOK remains a documented escape hatch for unlinked users; the composition — grant custody + attenuated minting + attribution + MCP conformance — is, to the best of this survey, novel as an integrated design.
